The self-improving flywheel

How a fix graduates from "ask first" to autonomous.

Auto-remediation is off by default and earned per fix-class through shadow-mode learning. A fix only becomes autonomous once it has proven itself and the local model can reproduce it — then the cloud dependency disappears entirely.

① OBSERVE the console + agent loop watch the cluster continuously
② DETECT & ACT propose a fix → ask on Telegram → apply on approval → log it
③ CAPTURE the incident→fix→outcome becomes a structured training row
④ TRAIN the Model Factory finetunes a local model on your own history
⑤ SERVE served behind a stable alias → the daily agent gets smarter
             └─────────► back to ① — every day a little smarter

Shadow → proving → learned → autonomous

A fix-class graduates only when ALL hold: ≥3 successes, ≥90% success rate, the local model reproduces it, a human enables it, and it's idempotent within the fence. A regression demotes it; flapping trips a circuit breaker back to human review.

Cloud is transitional, never permanent

When a novel issue needs a stronger model, the context passes a mandatory PII-redaction gate first. The cloud's fix then trains the local model — so the fix-class migrates from the cloud track to the fully-local, air-gap-safe track and stops needing the cloud at all.

Built-in updates and built-in support.

🔄

Settings → Updates

A firmware-style updater: every install shows its version, polls the public update channel every six hours, and lists what's new with the full changelog. The Update now button is shape-aware — the appliance pulls fresh images and recreates itself in place (watchtower), a native install pulls and restarts with live progress, and a Kubernetes install shows the exact helm upgrade to run. Air-gapped installs simply stay calm.

🎫

Settings → Support tickets

Something broken or missing? Raise it without leaving the app — text, image attachments, or a one-click screen capture. Tickets are recorded locally first (offline-safe, on the tamper-evident log), then filed straight onto the VKE issue tracker with the screenshots embedded — so the team is notified the moment you hit Send.

One build · three natures · an additive discipline
🍎

Native

Apple-silicon metal: MLX model serving and real MLX LoRA training — the fastest studio experience. A one-line macOS install (no Docker at all) is on the roadmap.

📦

Appliance

docker compose up on a Mac or a DGX — models, trainer and datasets bundled, fully offline after the pull.

⎈

In-cluster

One helm install into any Kubernetes — observing through its own ServiceAccount, read-only by RBAC.

The release discipline that makes one build serve all three: every change is additive — gated behind a flag with a safe default, degrading gracefully when a dependency is absent; nothing is ever renamed or removed. Releases are changelog-driven (the changelog's bullets become the update-channel highlights you see in Settings → Updates) and pass an automated additive gate: compile and lint across every module, then a bare-container smoke — the build must boot healthy with no cluster, no AI and no trainer attached, or nothing ships. One release command then keeps the source repo, the public artifact repo, the update channel and every install's Updates tab in lockstep.
Safety by construction

The strongest guarantee is the one you can't turn off.

A structural fence

Only deployment / statefulset / daemonset can be mutated; replicas are clamped to ≤20; and there is no delete code path anywhere — destructive actions are impossible, not merely disallowed.

Tamper-evident audit

Every observation, proposal, approval, action and outcome is written to an append-only, SHA-256 hash-chained event log. Editing any past row breaks every later hash — the Trust Center verifies the whole chain.

Human-in-the-loop by default

Auto-remediation is off out of the box. T0 (autonomous) is opt-in per fix-class and only for proven, idempotent, locally-reproduced fixes. Everything else asks first.

Role-based, PIN, no email

Six roles behind a PIN keypad — SRE lead approves, operator proposes (and can't self-approve), ML engineer owns the factory, exec gets read-only oversight. Contexts are read-only until explicitly set read-write.

Where it runs

On your cluster. Tailnet-secure. Your models, your data.

VKE runs as one process against any Kubernetes cluster via kubeconfig — Colima/k3s on a laptop, your on-prem cluster, or EKS/GKE. Inference runs on local models; nothing leaves the box unless a fix-class needs the transitional cloud track, and then only through the PII gate.

Two lanes, one codebase

On-prem — PM2 on a server, local models (MLX / Ollama) + the Claude CLI, zero egress. Cloud twin — the same app in Docker, cloud-API models behind the redaction gate, elastic GPU. You choose; the features and safety are identical.

Pluggable clusters & models

Point at a second cluster in minutes with no code change — the fence applies everywhere. The Model Factory runs embedded or standalone; finetunes go to local MLX by default, bursting to RunPod only when compute demands it.

kubeconfig→ read-only observe → fenced act (HITL) → event log → local finetune → k8s-sre alias → back to observe
