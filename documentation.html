VKE Documentation

What VKE is

VKE — the Virtual Kubernetes Engineer — is a self-improving SRE platform. It runs as one process against any Kubernetes cluster and unifies three faculties that a monitoring tool keeps separate: Observe (live cluster state + chat + prediction), Act (fenced remediation with human-in-the-loop approval), and Learn (its own incident history trains a local model that makes the engineer better every day). Every surface is a view over one append-only, tamper-evident event log.

Setup — the four ways to run VKE

Same product, same Training Studio, same update channel — pick the shape that fits the machine in front of you. Every install is equally easy to remove.

Which install for which machine

All container images and the Helm chart are multi-architecture (amd64 + arm64) from the same tag — Docker and Kubernetes pick the right build automatically; there is nothing architecture-specific to type.

1 · Native macOS — Apple silicon, MLX, no Docker

The fastest experience: Metal-speed model serving and real MLX LoRA finetunes in ~15 seconds. Installs into ~/.vke with a single launch agent — no sudo, no Docker.

curl -fsSL https://raw.githubusercontent.com/t4tarzan/vke-appliance/main/install-macos.sh | bash

First boot downloads ~1.2GB of models, then the browser opens on http://localhost:9040. Manage it with vke status · vke logs · vke stop; remove it completely with vke uninstall. Custom ports: prefix the installer with VKE_PORT=8080. Updates apply in one click from Settings → Updates (the app swaps its own bundle and restarts).

2 · Appliance — docker compose, everything bundled

Three images carry the app, the AI models and a real CPU trainer — fully offline after the pull, which makes this the shape for air-gapped sites and any machine with Docker (Mac, DGX, Linux — amd64 and arm64 alike, from the same tags).

Requirement: Docker Compose v2 (the docker compose plugin — check with docker compose version). The legacy Python docker-compose v1 fails on current images with KeyError: 'ContainerConfig'. If your distro only ships v1, install the plugin binary directly (no apt needed):

sudo mkdir -p /usr/local/lib/docker/cli-plugins
sudo curl -fsSL https://github.com/docker/compose/releases/latest/download/docker-compose-linux-$(uname -m) \
  -o /usr/local/lib/docker/cli-plugins/docker-compose
sudo chmod +x /usr/local/lib/docker/cli-plugins/docker-compose
curl -O https://raw.githubusercontent.com/t4tarzan/vke-appliance/main/docker-compose.yml
docker compose up -d
open http://localhost:9040

Custom bind/port: VKE_PORT=127.0.0.1:9062 docker compose up -d (loopback-only, e.g. behind your own nginx) or VKE_PORT=8080 for a plain port change. The first pull is ~13GB (the AI models travel inside the images) — allow ~20GB of free disk; after that the appliance runs with no internet at all.

Attach your real environment by uncommenting one line in the compose file — ~/.kube:/root/.kube:ro to observe your cluster, or the docker socket to list the host's containers (then Settings → Clusters → Discover). The bundled watchtower makes Settings → Updates a true in-place update. docker compose down -v is a factory reset; without -v your data and trained models survive restarts.

Fully air-gapped sites (zero internet, ever): every VKE release ships as a signed offline bundle — every image (models inside), the compose, the Helm chart, the docs and a local update channel in one artifact that travels on a disk. On the offline host: ./verify.sh (checks every byte against a cryptographically signed manifest, no network needed) then ./install.sh; for clusters, ./mirror-host.sh <your-registry> loads everything into your own Harbor/private registry. Every bundle is release-gated by a sealed acceptance walk — it boots and passes its full test inside a network Docker itself blocks. Bundles are delivered on request (~11GB). Future updates arrive as the next signed bundle and surface in Settings → Updates.

3 · In-cluster — one helm install into any Kubernetes

The product deploy: VKE runs inside your cluster and observes it through its own ServiceAccount — read-only by RBAC until you grant more.

The chart is published as a public OCI package — no repo clone, no credentials, works on x86 and ARM clusters alike (all images are multi-arch):

helm install vke oci://ghcr.io/t4tarzan/charts/vke --version 1.6.41 \
  --namespace vke --create-namespace \
  --set ai.baseUrl=http://<your-ollama-or-gateway>:11434 \
  --set ai.model=qwen2.5:7b

Useful values: clusterMode=demo (the bundled snapshot instead of live observe) · rbac.writeNamespaces={staging} (grant the fenced Act verbs in listed namespaces only — everywhere else the API server itself refuses) · trainer.enabled=true (the trainer sidecar: the Training Studio trains in-cluster and imports the result into your Ollama) · vllm.enabled=true (a GPU vLLM serving tier with zero-restart runtime-LoRA promotes — the high-throughput lane for hundreds of API users) · airgap.enabled=true (seal the platform: every internet egress off, updates from a local file:// channel) · service.nodePort (default 30940). Reach it via the NodePort or kubectl -n vke port-forward svc/vke 9040:9040. Updates are a helm upgrade (a pod can't replace its own image); removal is helm uninstall vke -n vke.

4 · Native (source) — the development shape

The reference install every release is cut from: the source checkout run by a process manager, with the full local model gateway and the MLX training factory. This is how VKE is developed — clients use the three shapes above. Sign-in for every shape: U-ML / 3333 (ML engineer) · U-LEAD / 1111 (SRE lead) · U-OPS / 2222 (operator) · U-DEMO / 0000 (read-only).

Features

VKE is one app of ~35 role-gated tiles across six lanes — Observe, Converse, Act, Learn, Oversight and Admin. Every surface is a view over the same append-only, hash-chained event log.

Observe — the cluster's live state

  • Cluster Overview — nodes ready · pods running · restarts · health rings, live.
  • Nodes — capacity, conditions and pressure signals, per node.
  • Workloads — deployments/statefulsets/daemonsets + pods; drill a pod to logs, describe and events in a side drawer.
  • Services — the host process fleet (pm2) with restarts, memory and logs, alongside Helm releases and Robot test suites.
  • Topology — the namespace → workload → pod → node graph.
  • Cluster Events — the live Kubernetes event stream, severity-filtered.
  • Alerts — rule-based watchers; each firing alert carries a normalized issue-signature.
  • Telemetry — Health · Metrics · Logs · Traces (OTel-ready; live from the cluster and the event log).
  • Discovery — cluster + cloud adapter registry (kubernetes live; AWS/Azure/GCP/RunWhen pluggable).
  • Cloud — multi-cloud account inventory (GKE/EKS/AKS · compute · databases · storage · load balancers).

Converse — ask the engineer

  • Chat — grounded in the live cluster and this cluster's own fix history; pick k8s-sre to answer from history, or deep·claude.
  • Three-section answers (trained model + live-cluster context ON) — ① the matching training-data rows, cited by dataset + row number; ② the live cluster (pulse chips, failing pods with your named workload flagged) + this cluster's learned fixes (✓ verified, success stats, fence) + matching field-guide cards; ③ a deterministic assessment — a 0–100 confidence meter, finding, likely cause, a recommended fix with one-click ⚡ Propose into the approval flow, and alternate causes — with the model's reasoning beneath it.
  • Confidence, scored honestly — every answer earns a number (verified-fix match 40 · the fix-class's real success rate ×20 · retrieval ×20 · replay 10 · corroboration 10; conflicting sources cap it). A question with no k8s jargon still grounds: the live cluster's observed failure reason joins the lookup automatically.
  • Playbooks — built-in runbooks plus cards generated from proven fixes.
  • Search — across pods, events, the event log and the knowledge base.

Act — remediate, with a human in the loop

  • Incidents — the six-section incident chart, keyed on the issue signature.
  • Approvals — the HITL queue; approve on screen or from Telegram (no self-approval).
  • Action Console — the one fenced mutation surface: scale · rollout-restart only.
  • Autonomy Board — T0/T1/T2 tiers, graduation gates and the circuit breaker (T0 off by default).
  • Predict — what's likely to fire next, from restart trends and pressure forecasts.

Learn — the factory (also runs standalone)

  • History — the append-only, hash-chained event log: the training corpus.
  • Knowledge Base — issue signatures × proven fixes × outcomes, plus the fix corpus panel: every retrievable fix with its provenance (bundled · playbook · learned · distilled), and one-click ✓ Verify that turns a candidate into grounding and a training target.
  • Day-one knowledge, baked in — every install ships knowing the canonical Kubernetes failures: 12 deep runbooks, 14 verified fix-corpus rows distilled from a real 3,300-incident EKS corpus (seeded at every boot), and the 40-card K8s Field Guide (restarts · rollouts · scaling · scheduling & nodes · namespaces/ports/DNS · RBAC · storage · probes) backing the reasoning on every shape, including sealed ones.
  • Knowledge — department documents + the estate's own ops history as collections, with span-level citations that deep-link to the exact passage; ingest by paste, semantic search where embeddings run.
  • Ask the Database — natural language over VKE's own records, any uploaded dataset's record store, or a read-only Postgres — every answer shows its exact SQL.
  • Datasets — build, consensus-verify and export SFT rows from the log — or upload your own (JSONL/CSV, normalized + PII-redacted, with append). Two curated starters ship in every picker: fixes-log-120 (real incidents → worked fixes, with refusals and hard negatives) and field-guide-qa (the generic guide as Q&A).
  • Training Studio — the five-step guided finetune flow: model → data → cost-gated train → watch → serve & chat — with a lineage lock (a model's run chain pins its base), visible continue-training, and a curriculum runner that trains ordered datasets as sequential resume runs on one model (details below).
  • Eval-gated promote — the exam grows itself from your own resolved incidents (every approved-and-verified fix harvests a case); a candidate that regresses against the current model is blocked from serving.
  • Models — aliases, hot-swap and the six-section model chart.
  • Benchmarks — the per-iteration leaderboard + replay-verify (Track B→A migration).
  • RAG — GPU-less specialization on your own history.
  • Iterative Demo — the v1 → v2 improvement story.
  • Agent Loop — the in-app scheduler: hourly sweep, daily audit/improve, history miner, graduation.

Oversight — the loop, measured

  • Analytics — KPIs, charts and trends folded from the event log.
  • Flywheel — fixes learned → reproduced locally → graduated to autonomous, plus the learning curve: coverage of seen failure classes, the 14-day confidence trend, and a projection of weeks to 80% coverage.
  • Knowledge gaps — every low-confidence answer records its question; the board lists the top gaps with one-click Distill (→ an unverified candidate for human review) or Dismiss. The model's ignorance writes its own curriculum.
  • Reports — daily audit and weekly review.
  • Trust Center — the fence, the tamper-evident audit chain, and the role matrix.
  • Documentation — this manual, in-app.

Admin — run the platform

  • Users & PINs — the roster and role access.
  • Clusters — kubeconfig contexts (read-only by default per context).
  • Git Sources — the GitOps source registry + sync.
  • Settings — model providers, the Telegram bot, the T0 master switch, and demo-configurable integrations (RunPod/SkyPilot burst · BYOK EKS/GKE · Prometheus/Loki/ClickHouse · PII-gated cloud model track).
  • Telegram Log — the HITL message mirror.

The Training Studio

The Finetune tile is a five-step guided studio (role ml_engineer / sre_lead) — designed so a newcomer can take a model from "picked" to "chatting with it" without knowing MLX, LoRA flags or GPU sizing.

  1. ① Model — every trainable MLX model on the box, with size, a fit note ("fast prototyping — ~20s local" … "high quality — minutes"), a recommended badge and its cloud-GPU floor. Fused finetunes appear too, so you can continue training on top of them.
  2. ② Data — the live SRE-history corpus, any saved dataset, or your own upload: JSONL in the common SFT shapes (messages · prompt/completion · instruction/output · Q&A), a two-column CSV/TSV or XLSX, pair-tag XML, a YAML list, or Q/A markdown. Rows are normalized to chat format and PII-anonymized (a reversible local vault — fix proposals are deanonymized so the applied fix carries the real values); append grows an existing dataset for the next run. See Data formats — one incident shown in every accepted shape.
  3. ③ Train — alias, iterations, learning rate, batch size and LoRA layers with sensible defaults, plus a compute choice. Nothing launches on the first click: "Estimate & train" returns the cost and wall-clock — local MLX is $0.00, a RunPod GPU shows its $/hr rate and total — and only the explicit Confirm & start button spends. Cloud GPUs stay greyed out until the Compute integration is switched on in Settings, and a model's GPU floor is enforced so a big model can never land on a too-small card.
  4. ④ Watch — the live loss curve and metrics, persisted on every poll so the curve survives a reload or server restart. Below it, the run history: click any past run to redraw its curve, and once two runs exist a real v1 → v2 overlay shows the improvement. A Retrain +data button sets the fused v1 as the base — v2 genuinely continues from v1's weights.
  5. ⑤ Serve & Chat — a finished run becomes a candidate behind its alias (the Track B→A gate). Promote hot-swaps the alias to the fused weights (or shows the exact one-paste gateway registration if the model isn't served yet), Test asks it a question right there, and Open in Chat hands you over to the full grounded chat.
The studio also feeds the Iterative Demo tile: once two real runs exist it stops showing the staged story and overlays your actual loss curves. And the whole factory — studio included — runs standalone on its own port (same code, same data), for deployments that only want the fine-tuning product.

Continuing, chaining and staying safe

Continue training — step ① lists your existing models ("continue: k8s-sre · 3 runs · resumes · trained through: a → b"); picking one locks the model and its base together, and the run resumes the saved adapter, so version n+1 starts from what version n learned. Curriculum — "＋ stage" on any dataset in step ② builds an ordered chain (e.g. your-logs → fixes-log-120 → field-guide-qa) trained as sequential resume runs on one model, advancing automatically as each stage succeeds; step ④ shows "stage x/y" and the run history is the chain's own record. The lineage lock — an existing run chain pins its base model: retraining defaults to it, and switching bases is refused loudly (it would corrupt the carried weights) unless you explicitly start a new model name.

The studio manual — from CSV to answers

One import feeds two lanes. Your CSV becomes a record store (every row, original columns preserved — where the facts live) and a training view (chat pairs: the other columns become the question, the auto-picked target column — reason / answer / label / fix… — becomes the answer; persona-stamped, PII-redacted, with a saved recipe so the same records can be re-targeted later). Training consumes the view; inference retrieves from the record store.

The one idea everything follows from: training teaches the model the task (format, persona, classification habit); the record store carries the facts. A model trained on 10,000 crash rows cannot recall row 4,317 and cannot say "I don't know" — retrieval can do both. That's why a trained model's answers open with ① rows from its own dataset, cited by row number, and why appending data updates answers instantly while the weights only need the next retrain.

Batch size & iterations — the coverage math

A run sees iterations × batch sample visits; one full pass over the data ("one epoch") needs rows ÷ batch iterations. The studio prints this as a coverage warning when your settings under- or over-shoot. All timings below are from real runs:

Dataset sizebatchiterationsThat isVerified timing
≤ 60 rows (runbooks, curated fixes)230–601–2 epochsGranite 20 it: 98s GPU / 651s CPU · Qwen-0.5B 60 it: ~9s
100 – 1,000 rows2–4≈ rows ÷ batch~1 epochQwen-0.5B: minutes on CPU
~10,000 rows (telemetry)42,500exactly 1 epochQwen-0.5B: 684s, val loss 0.018
  • Aim for about one epoch. Under it, big datasets are barely sampled (60×2 visits see 1.2% of a 10k set). Over it, 5–10 epochs on a small set destroys the end-of-turn habit and the model loops on novel questions — a repeat-penalty damper ships in every trained import, but don't rely on it.
  • Watch validation loss, not train loss. Falling = learning; rising while train falls = memorizing — stop or cut iterations. Good runs: val 0.018 (10k rows · 1 epoch), val ~0.4 (60 rows).
  • Learning rate 2e-4 is the default and rarely needs touching.
  • Appending data: "Retrain +data" continues from the fused v1 (a real v2 started at loss 0.41 where v1 started at 1.49) — and give appended rows enough iterations to compete with memorized ones (a real append needed 240 where 80 underfit).

What happens at inference

  1. Your alias resolves to base + adapter.
  2. ① deterministic retrieval over the record store → matching rows cited [row N] (workload-shaped tokens dominate the match — asking about payments-api-7f9 finds that pod's rows).
  3. ② live-cluster toggle ON → cluster brief + proven-fix corpus + semantic RAG; OFF → the model may use nothing beyond the ① rows.
  4. ③ the model answers under the persona it was trained with, streamed with citations plus confidence and source-conflict chips (computed from the grounding, never by the model).
  5. For exact counts and aggregates, skip the model: Ask the Database runs real SQL over the same record store, receipt shown.

How VKE learns — day one to autonomous

Small local models don't get better at facts by training — they get better because the system around them compounds: retrieval answers the facts · training teaches the format and reasoning pattern · verification turns "an answer" into a high-confidence answer. Four deterministic loops (no extra models) make that measurable:

  • Every answer is scored (0–100) and the scores are kept — the daily average is the maturity signal, on the Flywheel board.
  • The exam grows itself — every approved fix whose outcome came back OK harvests an eval case; promotes are judged against your resolved incidents.
  • Dry-ups become work items — a low-confidence answer records its question in the gap ledger ("asked 7×, the model had nothing"), one click distills a candidate for human review.
  • The learning curve is on the board — coverage of seen failure classes, the 14-day confidence trend, and the projected weeks to 80% coverage.

The throttle on risk never moves: the five graduation gates, the T0 master switch, the per-class circuit breaker and the mutation fence stand between a confident answer and an autonomous action — confidence buys proposals; verification buys autonomy.

Operating cadence — daily: work the approvals queue honestly (approve → outcome is the flywheel's fuel). Weekly: clear the gap ledger; replay-verify anything with ≥3 successes. Monthly: retrain (the nightly auto-retrain does it once the eval set exists) and read the curve.

The six lanes

  • Observe — Cluster overview (KPIs + health rings), nodes, workloads (tap a pod → its logs, describe and events slide in from the right), topology, cluster events, alerts, telemetry, discovery adapters.
  • Converse — Chat grounded in the live cluster + your proven-fix history (pick k8s-sre or a deep reasoning lane); playbooks; estate-wide search.
  • Act — Incidents (a six-section stepper from Signal → Learning), the HITL approval worklist, the fenced action console, the autonomy board, and the predictive engine.
  • Learn — History (the event log), the knowledge base of signatures × fixes, the dataset builder, finetune with a live loss curve, the served models (a stepper model-chart), benchmarks, RAG, the iterative-improvement demo, and the agent loop.
  • Oversight — The analytics dashboard, the flywheel centerpiece, daily/weekly reports, and the Trust Center.
  • Admin — Users & PINs, Clusters (kubeconfig contexts), Settings, and the Telegram log.

A day in the loop

  1. A workload starts crash-looping. The agent loop detects it and files an incident with a normalized signature.
  2. An operator asks the engineer in chat; the answer is grounded in this cluster's own history ("we've fixed this before — rollout-restart worked 100%").
  3. They propose the fix. It lands in the approval queue and, if a bot is configured, on Telegram with ✅ / ❌ buttons.
  4. An sre_lead approves (from the app or their phone). The fenced action runs and its outcome is logged to the hash chain.
  5. The knowledge base counter increments; the incident feeds the dataset. After a finetune the local model reproduces the fix — and once it's proven, the fix-class can graduate to autonomous.

Technical architecture

A FastAPI backend serves a vanilla-JS PWA and a versioned /v1 JSON API. The three source systems it replaces — an SRE console, an external cron "Hermes" loop, and a Model Factory — collapse into one process with one SQLite database, so the cross-service HTTP hops and file-drops dissolve into direct table reads and an in-app scheduler.

Browser (PIN + role)
  → FastAPI :9040  ── static PWA + /v1 JSON
      ├─ cluster.py   read-only kubectl (kubeconfig-pluggable)
      ├─ chat.py      → Switchboard model gateway + deep-reasoning lane
      ├─ events.py    append-only SHA-256 hash-chained event log  (the corpus)
      ├─ actions.py   THE mutation chokepoint — the fence (no delete path)
      ├─ agentloop.py in-app scheduler (sweep · audit · improve · miner · graduation)
      ├─ policy.py    T0/T1/T2 tiers + graduation gates + circuit breaker
      └─ factory/     data → MLX finetune → stable /v1 alias  (embedded + standalone :9041)

The safety fence

Every mutation goes through one chokepoint (actions.py) with structural guarantees:

  • Allowed kinds: deployment, statefulset, daemonset — nothing else can be mutated.
  • Replica clamp: MAX_SCALE_REPLICAS = 20, always applied.
  • No delete route exists — there is no code path to delete a workload, PVC, or namespace. T2 (never-auto) is structural, not a list.
  • Tiers: T0 auto (proven idempotent fixes only, off by default), T1 human-in-the-loop (default), T2 never-auto. A circuit breaker demotes a flapping auto-fix back to human review.

How the public URLs work (the house pattern): each *.dkube.app is a thin Vercel front that rewrites every path to a Tailscale funnel, where one Caddy strips an internal path prefix and routes to the right app port — vkeapp → /__vke/ → :9040, vkecloud → /__vkecloud/ → :9060. For the live demo both lanes run on the same box behind the funnel; the twin stays fully VPS-portable (deploy/twin/DEPLOY.md) — relocating it is just moving the Vercel rewrite target.
